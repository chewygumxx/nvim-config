existing `vim.bo[buf].filetype == "markdown"` equality check already guarantees
for `markdown.claude` and `markdown.nex-note`; and `foldlevel` comes from
`util.modeline.base`'s `append` argument, exactly as `util.nex` passes it today.

`tests/test_util_header.lua`'s "wraps a markdown header in frontmatter" case
needs rewriting against the new shape, and `tests/test_util_nex.lua` must still
pass unchanged, which is the evidence the extraction preserved nex's output.
Headers are also rewritten in CI by the external
`chewygumxx/sync-header-metadata@v2` action, and the two `.md` files already
carrying `__cgxx` frontmatter have survived it, so no workflow change is
expected; confirm on the next push rather than assuming.

## Phase 2: Features

### 2.1 Colourise the statusline git segment

`lua/util/statusline.lua` currently emits one plain `%{}` and documents at
length why it must never be the re-parsing `%{%...%}` form. Colour therefore
cannot come from the data. Split the notation into three items instead, each
value still unparsed, with the highlight items sitting in the format string
between them:

```lua
M.items = "%<"
    .. "%#CgxxStatuslineSlug#%{v:lua.require'util.statusline'.slug()}"
    .. "%#CgxxStatuslineBranch#%{v:lua.require'util.statusline'.branch()}"
    .. "%#CgxxStatuslinePath#%{v:lua.require'util.statusline'.path()}"
    .. "%#StatusLine#"
    .. "%{%v:lua.require'util.statusline'.fallback()%}"
```

Keep the cache a **single string** and slice it in the three accessors. Do not
cache a table: `store` guards against a redraw livelock by comparing the new
value with `vim.b[bufnr].cgxx_statusline`, and a table read back from `vim.b`
never compares equal to the one written, so the guard would fail open and every
redraw would schedule another. Slicing left to right on `:` is unambiguous
because git forbids `:` in both a slug and a ref name, while a filename may
contain one: first `:` ends the slug, second ends the branch, the remainder is
the path.

Define `CgxxStatuslineSlug`, `CgxxStatuslineBranch` and `CgxxStatuslinePath` in
`lua/highlight.lua`'s `hlgroup_defs`, which runs last in `init.lua` precisely so
it outranks the colorscheme. Each needs `bg` matching `StatusLine` rather than
`none`, or the segment will punch holes in the statusline.

`tests/test_util_statusline.lua` covers all three load-bearing decisions; extend
it with the split accessors, a case proving a `%` in a filename still survives,
and a case proving the `%#` items appear in `M.value()`'s output at the position
`%<%f` occupied.

Commit: `feat(util): Colourise the statusline segment`

### 2.2 Colourise git commit buffers

`gitcommit` currently routes to `lua/filetype/prose.lua` in
`lua/filetype/init.lua`'s `M.modmap`. Add `lua/filetype/gitcommit.lua` and route
both `gitcommit` and `gitrebase` to it. The dispatcher runs exactly one module
per filetype, so carry prose's `spell = true` across rather than expecting
inheritance, the way `filetype.nex_note` copies from `filetype.markdown`.

Segment colouring goes through `mini.hipatterns`, which is already installed and
configured in `lua/spec/mini.hipatterns.lua`, using a buffer-local
`vim.b.minihipatterns_config` set from the module's `M.setup`: the Conventional
Commit type, the `(scope)` group, the `:` delimiter, the subject, and the
overflow past `header-max-length` so the 50 character cap this repo enforces is
visible while typing. `hlgroup_defs` declares the groups, and the dispatcher
applies them once per session.

Add the module to `tests/test_coverage.lua`'s `covered_by` registry pointing at
`tests/test_filetype_modules.lua`, and drive it there through `filetype.config`
like its siblings.

Commit: `feat(ft): Colourise git commit buffers`
